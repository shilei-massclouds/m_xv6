# 两条 Flow 的并发路径覆盖

状态：暂缓。本文记录已确认的模型边界和下次讨论的起点，尚未证明完全覆盖。

## 讨论范围

- 私有 Actions 有独占承诺，其内部交错不是模型允许的路径，因此内部普通操作不设 I/O 点。显式 `break` 按既定语义暂停和恢复。具体设点规则见 [spec 说明](../framework/SPEC.md)。
- 覆盖的基本问题是：从任一可达状态出发，如果某条 Flow 可以合法地执行下一步，推导器是否一定能得到相应的后继状态？
- 后继状态需要比较 GV、每条 Flow 的待执行位置及其 Env、Signal 和通知事实。最终 GV 相同，并不意味着中间状态或后续选择相同。若两条路径的状态及可用后续确实等价，可以只保留一条继续推导；这与逐条保留所有执行历史是两个目标。

## 当前结论和待验证点

现有推导允许派生 O 点回接已参与过的 Flow，例如 `BP → AP → BP`。队列为空时结束，只能说明当前组合规则不再产生新分支。BP/AP 曾推导到第 11 阶，这个结果本身不证明完全覆盖。

1. **回接入口是否齐全。** [当前实现](../framework/derivation.py)把 O 点关联到以它为最近输出的首个 I 点。需要确认每个合法切换都可由某个这样的关联表示。可以先看内层操作和外层 `drive` 都保存 O 点、两次保存之间没有 I 点的情况。
2. **筛选是否遗漏合法顺序。** O 点的 `waits_for` 必须由目标 I 点的 `notified` 满足，按实例名匹配，例如 `smp_started`。如果某份独立 O 快照没有继承目标线路已经发生的通知，需要验证相应的合法顺序是否能由派生 O 点回接得到。
3. **去重是否保留后续选择。** 比较被判为重复的两个状态，看它们是否允许相同的下一步。只比较 GV 摘要不足以回答这个问题。

## 恢复讨论时的第一个用例

写两条短 Flow：BP 发出通知后还有一个操作；AP 在 `wait` 前有一个准备操作，等待成功后还有一个操作。把私有 Actions 当作原子步骤，手工列出小模型的可达状态和每个状态允许的下一步，再与推导器逐项比较。至少检查「AP 先准备，再由 BP 通知」和「BP 先通知，AP 准备，随后 BP 继续」两种顺序。若有差异，记录第一条缺失的合法切换，以及它对应的 GV、I/O 点和通知事实。
